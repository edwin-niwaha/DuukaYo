# Deployment guide (no deployment performed)

Build the API and web images separately using each project's Dockerfile. Deploy one shared API and web service for all retailers; route public shops by slug. Use managed PostgreSQL with encrypted backups and recovery drills, private Redis, a Celery worker, and exactly one Celery beat scheduler. API image can run `celery -A config worker -l INFO` or `celery -A config beat -l INFO`. Apply migrations as a release job before rolling API workers. Never run demo seeding in production.

Set API `DJANGO_SETTINGS_MODULE=config.settings.production`, a random 40+ character SECRET_KEY, DATABASE_URL, REDIS_URL, explicit ALLOWED_HOSTS and HTTPS CSRF_TRUSTED_ORIGINS. Terminate TLS at a trusted proxy which removes client-supplied X-Forwarded-Proto and sets it correctly. API trusts that header only in production. Configure the web API_URL to the API service origin and WEB_ORIGIN to the exact public HTTPS web origin. Cookies are Secure, HttpOnly for the session, SameSite=Lax. The web proxy rejects mutation origins other than WEB_ORIGIN; Django checks CSRF tokens too. No browser bearer token storage.

Serve the API privately behind the web proxy where possible, with a separately TLS-protected mobile API origin. The proxy must forward the public origin for CSRF. Restrict ingress, configure shared rate limiting at the gateway, request size limits and monitoring. The in-process DRF throttle is a development safeguard, not distributed abuse protection. Avoid logging cookies, JWTs, request bodies or guest order capability URLs. Set `Cache-Control: no-store` and `Referrer-Policy: no-referrer` for guest order pages and API responses.

FCM: provision a project and server service account only when ready. Mount credentials as a secret and set GOOGLE_APPLICATION_CREDENTIALS plus PUSH_BACKEND=fcm. Supply the Android Firebase app configuration locally via app.config and googleServicesFile when making a native development build. No Firebase credentials are committed. The backend uses Firebase only for push; PostgreSQL is the sole business store (firebase-admin brings Firestore as an unused transitive dependency). Notification payloads contain identifiers, and clients retrieve authorized order details from Django. Refresh remains the fallback when push fails.

Build Android with Expo development builds first. Use HTTPS EXPO_PUBLIC_API_URL in production and EXPO_PUBLIC_ENV=production. EAS profiles are supplied; no EAS project, signing keys, upload or paid build has been created. Test actual Android SQLite lifecycle, secure storage, notifications and share sheets before distribution. Physical printing is deferred until a specific printer has been integrated and tested.

Payments remain manual. Future provider adapters need per-merchant onboarding, verified callbacks, idempotent reconciliation and direct merchant settlement. Perpetual Labs does not collect merchant revenue by default. This MVP makes no tax certification or production-readiness claim.
